## Codex Provider Adapter

1. Require one explicit Trade Journal research insight ID. From the Trade Journal root, use Codex's repository command runner for `npx tsx scripts/belief-research-relation.ts --prepare --insight-id <uuid>`. Continue only when it returns `status: ready`; otherwise return the exact unavailable result. Bind every recommendation to the exact `contextDigest`, Notes source/content digest, Toulmin evidence, claim resolutions, developing and monitoring thesis argument digests, and existing relationships.
2. Preserve authority exactly. Notes/Tana owns capture, source material, and Toulmin extraction. Trade Journal owns promoted investment claims, theses, governed claim-thesis relationships, publication state, unresolved Decision Items, and journal audit. Do not treat provider output as repository fact, semantic proof, persistence, authorization, or a completed relationship.
3. Resolve the Registry-locked claims-synthesis and research-publication Capabilities. Exact `(sourceInsightId, sourceClaimId)` provenance is identity regardless of claim lifecycle status: reuse the existing promoted claim and never duplicate a Notes-owned source claim. A semantic relation can name only an exact existing promoted claim or a promoted claim already created by an accepted research-publication result. This adapter cannot publish claims.
4. Judge only direct semantic bearing between the exact source claim assertion and a governed developing-or-monitoring thesis core argument, driver, or assumption. A relationship must be `supports`, `refutes`, or `foundation`, preserve honest high, medium, or low confidence and rationale, and include exact claim and thesis anchors plus the causal, evidential, qualifying, or refuting connection. Every refuting relation must also surface an unresolved `review_refuting_claim` Decision Item. Medium- or low-confidence supporting or foundational relations must also surface an unresolved `confirm_claim_link` Decision Item. Holdings are not an information gate. Ticker overlap, keyword overlap, and provider recommendation are never semantic proof.
5. Preserve source evidence, reasoning, backing, qualifier, every rebuttal, time horizon, relationship rationale, audit context, and explicit ambiguity. Cover every source claim with bounded direct relations, an explicit `claim_identity` or `thesis_bearing` ambiguity, or an unrelated rationale. Do not silently link an ambiguous claim and do not invent missing identity or judgment.
6. Validate the recommendation-only result by using Codex's repository command runner for `npx tsx scripts/belief-research-relation.ts --validate-result <file|-> --context <file>`. Then prepare the exact persistence boundary by using Codex's repository command runner for `npx tsx scripts/belief-research-relation.ts --prepare-recording --result <file|-> --context <file>`. Claim-publication requirements remain exclusions. Only exact existing-claim relationships and unresolved Decision Item candidates can proceed; preparation deterministically adds the required refuting-evidence and tentative-link Decision Items.
7. Present the exact bounded relationship and Decision Item candidates to the current user. Only after that user explicitly accepts exact relation and decision IDs may this interactive adapter serialize a version `1.0.0` `belief_research_relation_authorization` token. It must set `authorizedBy` to `user`, use a fresh UUID, canonical ISO instants no more than 24 hours apart, bind `recordingDigest`, name unique `acceptedRelationIds` and `acceptedDecisionIds`, and use the exact emitted statement. Never infer, fabricate, broaden, reuse for different canonical content, or self-authorize a token.
8. Validate the token without writes by using Codex's repository command runner for `npx tsx scripts/belief-research-relation.ts --validate-authorization <file|-> --recording <file>`. Validation is readiness only. On missing user acceptance, malformed or expired authority, stale bytes, unavailable input, sandbox denial, or user refusal, stop with no writes.
9. When and only when the exact validated token encodes the current user's explicit decision, pipe `{ "prepared": <exact prepared recording>, "authorization": <exact token> }` once to `npx tsx scripts/ops/record-belief-research-relation.ts --stdin`. Treat a non-zero result as failed and do not attempt another mutation route. Retry an uncertain response only with canonically identical authorization JSON.
10. The recorder is the sole mutation boundary. Its serializable transaction may reuse or insert only exact `claim_thesis_mappings`, insert accepted unresolved `decision_required` `journal_entries` with `resolution: null`, and insert one `belief_research_relation_recorded` audit containing digest-bound authorization, candidates, actual records, exclusions, permitted write surface, and forbidden authority. It revalidates current provenance and thesis eligibility, returns exact dispositions, retries safe races, is idempotent, and rolls back partial failure.
11. This adapter must not create or mutate `main_claims`, artifacts, insights, theses or thesis status, signals, strategies, positions, orders, or trades; must not resolve a Decision Item; must not use ad-hoc SQL or Drizzle writes, Supabase MCP writes, direct API mutation, generic writers, or temporary write scripts; and has no scheduler, credential, provider-discovery, active-operational, or trade authority.

Unattended execution may prepare or validate recommendation-only output and return explicit ambiguity. It must not create an authorization token, invoke the recorder, persist a link or Decision Item, resolve judgment, or change status. Return `writes: []`.
