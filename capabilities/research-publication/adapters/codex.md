## Codex Provider Adapter

1. Require one explicit Trade Journal research insight ID and one already validated recommendation-only result from the Registry-resolved `capability:scope:trade-journal/claims-synthesis`. Claims synthesis is input recommendation, never publication authorization.
2. From the Trade Journal root, use Codex's repository command runner for `npx tsx scripts/research-publication.ts --prepare --insight-id <uuid> --synthesis-result <file|->`. Continue only when it returns `status: authorization_required`; otherwise return the exact unavailable result. Bind all work to its `publicationDigest`, current Notes source digest, claims-synthesis result digest, candidates, exclusions, and exact permitted write surface.
3. Preserve authority and meaning exactly. Notes/Tana owns capture, source material, and Toulmin extraction. Trade Journal owns promoted investment entities, publication state, and governed relationships. Keep `sourceEvidence`, `synthesizedRecommendations`, `claimCandidates`, the user's publication decision, and `relationshipCandidates` distinct. Never describe a recommendation, readiness result, or token proposal as a completed publication.
4. Exact `(sourceInsightId, sourceClaimId)` provenance is deterministic identity. Reuse an existing provenance-bearing claim regardless of lifecycle status and never duplicate it. A new draft claim candidate must preserve evidence, reasoning, backing, qualifier, every rebuttal, time horizon, tickers, and synthesis rationale. Do not use ticker or keyword overlap as semantic proof.
5. Do not offer excluded, claim-identity-ambiguous, or thesis-bearing-ambiguous material for publication. Every accepted claim must have at least one unambiguous accepted developing-or-monitoring macro or asset thesis relationship. Use only the exact prepared candidate IDs; do not invent claims, mappings, or missing judgment.
6. Present the exact bounded candidate selection to the current user. Only after that user explicitly accepts exact claim refs and relationship IDs may this interactive adapter serialize that decision into the version `1.0.0` `research_publication_authorization` token. It must set `authorizedBy` to `user`, use a fresh UUID, canonical ISO instants no more than 24 hours apart, bind the exact `publicationDigest`, name unique `acceptedClaimRefs` and `acceptedRelationshipIds`, contain every and only claim used by an accepted relationship, and use the exact statement emitted by the prepared contract. Never infer, fabricate, broaden, reuse for different bytes, or self-authorize a token.
7. Validate the token without writes by using Codex's repository command runner for `npx tsx scripts/research-publication.ts --validate-authorization <file|-> --publication <file>`. Validation means authorization readiness only. On missing user acceptance, malformed or expired authority, stale bytes, unavailable input, sandbox denial, or user refusal, stop with no writes.
8. When and only when the exact validated token encodes the current user's explicit decision, pipe `{ "prepared": <exact prepared result>, "authorization": <exact token> }` once to `npx tsx scripts/ops/publish-research.ts --stdin`. Treat a non-zero result as failed; do not attempt a different mutation route. Exact retry after an uncertain response is safe only with byte-identical authorization.
9. The recorder is the sole mutation boundary. Its serializable transaction may reuse or insert accepted `main_claims` rows, reuse or insert accepted `claim_thesis_mappings`, and insert one `research_publication_recorded` `journal_entries` audit. It revalidates current state, refuses conflicts or drift, returns exact created/reused dispositions, and rolls back partial failure.
10. This adapter must not use ad-hoc SQL or Drizzle writes, Supabase MCP writes, direct API mutation, generic write helpers, temporary write scripts, legacy Obsidian paths, removed intelligence-report or triage systems, or stale views terminology; must not write artifacts, insights, evidence links, theses, signals, Decision Items, strategies, positions, orders, or trades; must not change any entity or thesis status or resolve any Decision Item; and has no scheduler, credential, provider-discovery, live-operational, or trade authority.

Unattended execution may prepare or validate only and must return `authorization_required` or an exact unavailable/refused result with `writes: []`. It cannot create an authorization token or invoke the recorder because candidate acceptance and thesis-bearing acceptance are genuine user judgment.
