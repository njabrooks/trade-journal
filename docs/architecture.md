## 1. Purpose

This document defines the high-level architecture for the Trade Journal / Weekly Options Review app. It translates the Project Plan v1.0 and the existing `WeeklyOptionsReview.xlsx` workbook into a concrete system design that can be implemented in a Next.js + Supabase stack.

The focus is on:

- Core layers and responsibilities
- Data flow from brokers → database → UI
- Boundaries between frontend, backend, and background jobs

---

## 2. System Overview

The system is a full-stack TypeScript application built on:

- **Next.js (App Router)** for UI and server logic
- **Supabase (Postgres)** for persistent storage and auth
- **Supabase MCP** for schema management, migrations, and type generation
- **Drizzle ORM** (or Supabase client) for runtime database queries
- **Optional background worker / edge functions** for ingestion

High-level flow:

1. **Ingestion layer** pulls or receives data from broker sources (e.g. IBKR Flex, CSV uploads).
2. Data is written into **normalized core tables** in Supabase (trades, positions, MTM, cash, etc.).
3. **Domain logic layer** aggregates and derives strategy-level metrics (PnL, exposures, states).
4. The **Next.js app** exposes:
   - Dashboards for portfolio and strategy triage
   - Detail views for strategies and trades
   - Review & journaling workflows

## 3. Logical Layers

### 3.1 Presentation Layer (Next.js App)

- Responsible for:
  - Routing (`app/*`)
  - Rendering dashboards, tables, forms
  - Orchestrating user workflows (new strategy, triage, close-out)

- Interaction patterns:
  - Server Components use Drizzle ORM (or Supabase client) to fetch data from the database
  - Data access functions in `lib/services/` or `db/queries/` encapsulate queries
  - Client Components wrap interactive controls (filters, modals, charts)
  - Client-side queries use Supabase client with RLS policies

### 3.2 Domain / Application Layer

Implemented as plain TypeScript modules under `lib/`:

- **Domain models**:
  - Strategy, StrategyTemplate, Position, Trade, DailySnapshot, TriageRecord, BlotterAction, etc.
- **Use-cases / services**:
  - `openStrategy()`, `updateStrategyState()`, `recordBlotterAction()`
  - `getStrategyOverview()`, `getTriageQueue()`, etc.
- **Business rules**:
  - Strategy lifecycle state machine
  - Triage classifications
  - Aggregation of trades → positions → strategy metrics

This layer is **framework-agnostic** and should not depend on React/Next.

### 3.3 Data Access Layer

- Responsible for **reading/writing** from Supabase (Postgres) at runtime.

**Two-Tier Architecture**:

1. **Schema Management (MCP)**:
   - Migrations and schema changes via Supabase MCP
   - Type generation via MCP (exports TypeScript types)
   - Database administration, introspection, and edge function deployment
   - **Not used for runtime queries** - MCP is a dev/admin tool

2. **Runtime Queries (Drizzle ORM / Supabase Client)**:
   - Drizzle ORM for type-safe queries from Server Components and API routes
   - Supabase client (`@supabase/supabase-js`) as alternative for simpler cases
   - Types generated by MCP are imported into Drizzle schema/queries
   - Query functions in `db/queries/` or `lib/services/` encapsulate database access

Responsibilities:

- Define table schemas and relationships (via MCP migrations)
- Provide typed query functions using Drizzle ORM:
  - e.g. `getStrategiesWithLatestSnapshot()`
  - `insertTradesFromCsvUpload()`
- Ensure type safety by importing MCP-generated types into Drizzle schemas

**Clear Separation**: MCP handles schema/admin (development), Drizzle handles queries (runtime).

### 3.4 Ingestion / Integration Layer

- Entry points for external data sources:
  - Manual CSV uploads in the UI
  - Scheduled jobs calling the IBKR Flex API (later)

Responsibilities:

- Validate and parse external data.
- Map raw records into internal entities (Trade, Position, CashFlow).
- Handle idempotency (avoid duplicate inserts).

Location:

- UI upload handlers: `app/api/uploads/*`
- Background jobs: separate folder/repo or Supabase Edge Functions, but use the same domain mapping functions as the main app.

## 4. Data Flow (v0 Simplified)

1. User uploads a CSV export (e.g. Flex data).
2. API route parses the file, normalizes rows, and uses Drizzle ORM to persist them in core tables (`trades`, `positions`, `cash_flows`, etc.).
3. A background or on-demand process computes:
   - Daily snapshots
   - Strategy-level aggregates
4. UI pages (Server Components) read from:
   - **Core entities** via Drizzle ORM queries, with **precomputed metrics** for fast rendering.

**Schema Changes**: Handled separately via MCP migrations, then types are regenerated and imported into the runtime codebase.

---

## 5. Key Architectural Decisions

- **Co-locate API and UI** in a single Next.js app for simplicity.
- Keep **domain logic pure** (plain TS) so it can be reused by:
  - Server actions
  - Route handlers
  - Background workers / cron jobs
- Prefer **precomputed, append-only metrics** (daily snapshots, blotter actions) for path-dependent analytics, rather than recomputing everything on every request.

## 6. Future Extensions (Post-v1)

- Multi-user tenancy and RLS policies in Supabase.
- Automated IBKR Flex ingestion via cron.
- More sophisticated analytics (path dependence, MFE/MAE, playbook backtesting).
